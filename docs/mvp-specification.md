# 1. 目的

本システムは、カメラ映像から利用者のポーズやモーションを認識し、あらかじめ紐付けられた家電操作または外部HTTP APIを実行するスマートホーム操作基盤である。

MVPでは、ユーザーが新しいポーズやモーションを登録する機能は実装せず、認識対象となる動作は開発時にあらかじめ定義しておく。

# 2. MVPの範囲

| **含める機能**                                       | **含めない機能**                              |
|------------------------------------------------------|-----------------------------------------------|
| ・XIAO ESP32S3 Sense 2台からのHTTP MJPEG配信         | ・ポーズ・モーションの追加登録画面            |
| ・PythonによるMJPEG受信                              | ・録画による学習・DTW・機械学習モデルの再学習 |
| ・MediaPipe PoseおよびHandsによる認識                | ・横向き・背面方向の認識                      |
| ・正面方向を前提とした固定ポーズ・固定モーション判定 | ・個人識別                                    |
| ・PythonからGoへの認識イベント送信                   | ・同一カメラ内での複数人同時操作              |
| ・GoによるDB参照、紐付け、クールダウン、操作実行     | ・カメラ2台の映像統合や3D復元                 |
| ・自作赤外線端末または一般的なHTTP APIの呼び出し     | ・WebRTC・UDP独自映像転送                     |
| ・カメラごとに異なる操作の割り当て                   |                                               |
| ・操作結果およびエラーのログ記録                     | ・赤外線信号の学習機能                        |
| ・操作ログのリアルタイム表示                         |                                               |

# 3. 利用前提

- カメラは2台使用し、それぞれ別の場所または別のデモ領域に設置する。
- 各カメラは独立して動作し、同一人物を別角度から撮影する用途には使用しない。
- 人物はカメラ正面付近に立ち、上半身または全身と手が画面内に入ることを前提とする。
- 各カメラにつき、同時に操作対象となる人物は原則1人とする。
- カメラ、認識サーバー、操作対象機器は同一LAN内で動作させる。
- 映像は保存しない。

# 4. システム構成

```text
XIAO ESP32S3 Sense #1 ──HTTP MJPEG──> Python Worker #1 ┐
                                                            │
XIAO ESP32S3 Sense #2 ──HTTP MJPEG──> Python Worker #2 ├─HTTP/JSON─> Go API
                                                            │                │
                                                            └────────────────┘
                                                                             ↓
                                                                       PostgreSQL
                                                                             ↓
                                                     自作赤外線端末 / 外部HTTP API
                                                                             ↓
                                                                      家電・機器操作
```

# 5. コンポーネント仕様

## 5.1 カメラ端末

| **項目**           | **仕様**                                                 |
|--------------------|----------------------------------------------------------|
| **端末**           | Seeed Studio XIAO ESP32S3 Sense × 2台                    |
| **役割**           | カメラ映像の取得とHTTP MJPEG配信のみ                     |
| **通信**           | HTTP MJPEG                                               |
| **フレームレート** | 10〜15fpsを目標。実機で安定した値を採用する              |
| **解像度**         | 320×240または640×480を初期候補とし、負荷と精度で調整する |
| **再接続**         | Wi-Fi切断後は自動再接続を試みる                          |
| **映像保存**       | 行わない                                                 |

## 5.2 Python認識サービス

- カメラごとに独立したワーカーを1つ起動する。
- 各ワーカーは対象カメラのMJPEGストリームを直接受信する。
- MediaPipe PoseとMediaPipe Handsを使用する。
- PoseとHandsは原則として各フレームで実行し、負荷が高い場合のみHandsの実行頻度を落とす。
- 認識対象は、正面方向からの固定ポーズ・固定モーションとする。
- 認識した結果のみをGoバックエンドへHTTP/JSONで送信する。
- カメラ切断時は指数バックオフで再接続する。
- 古いフレームをためず、最新フレームを優先する。

## 5.3 Goバックエンド

- 言語はGo、WebフレームワークはEchoを使用する。
- Pythonから認識イベントを受け取る。
- camera_idとmotion_codeを用いてDBから実行対象を検索する。
- 同じ操作の連続実行を防ぐため、クールダウンを管理する。
- 自作赤外線端末や外部HTTP APIを実行する。
- 家電、操作、モーション、紐付け、ログを管理する。
- フロントエンド向けREST APIを提供する。

## 5.4 PostgreSQL

MVPでは、以下のテーブルを使用する。

| **テーブル**          | **役割**                                             |
|-----------------------|------------------------------------------------------|
| **cameras**           | カメラID、設置場所、ストリームURL、有効状態を管理    |
| **motions**           | Python側で認識可能な固定ポーズ・固定モーションを管理 |
| **appliances**        | 操作対象の家電または機器を管理                       |
| **appliance_actions** | 家電に対する具体的な操作と実行方式を管理             |
| **motion_bindings**   | camera_id、motion_id、action_idの紐付けを管理        |
| **action_logs**       | 認識、操作結果、エラーを記録                         |

# 6. 認識仕様

MVPで使用する具体的なポーズ・モーション名と判定条件は、実装開始前または実装中に開発メンバー間で決定する。ただし、登録機能は作らず、Pythonコード内に固定ルールとして実装する。

- 静的ポーズは、関節位置、関節角度、手の形、および一定時間の維持で判定する。
- モーションは、複数の状態を順番に通過したかをステートマシンで判定する。
- Handsだけで判定せず、Pose条件と組み合わせて誤作動を抑える。
- 同じポーズを維持したまま再発火しないよう、通常姿勢へ戻るまで再認識を禁止する。
- Go側でも紐付け単位のクールダウンを適用する。

# 7. カメラごとの独立動作

2台のカメラは独立した入力元として扱う。認識結果には必ずcamera_idを含め、同じmotion_codeでもカメラごとに異なる操作を割り当てられるようにする。

```text
camera-1 + MOTION_A → リビング照明ON
camera-2 + MOTION_A → 扇風機ON
```

> 現行実装との差分（2026-08-05）: 現在のGoバックエンドは、`camera_id` をカメラの有効性確認とログに使用し、アクションの紐付けは `motion_id` ごとに1件のグローバル設定として扱う。`camera_id` は任意のメタデータとして保持するが、カメラごとの異なるアクション選択にはまだ使われない。そのため、上記のカメラ別割り当てを実現するには、紐付け画面・DB制約・検出時の解決ロジックを拡張する必要がある。

# 8. 通信仕様

## 8.1 カメラ → Python

- プロトコル: HTTP
- 形式: MJPEG
- 接続方向: PythonがカメラのストリームURLへ接続する
- 障害時: Python側で再接続する

## 8.2 Python → Go

エンドポイント例:

```http
POST /internal/detections
```

リクエスト例:

```json
{
  "event_id": "UUID",
  "camera_id": "demo-camera-1",
  "motion_code": "MOTION_CODE",
  "confidence": 0.93,
  "detected_at": "2026-08-03T15:00:00+09:00"
}
```

Go側はevent_idで重複処理を防止する。

## 8.3 Go → 操作対象

操作方式は特定の赤外線端末に限定せず、provider_typeに応じて実行処理を切り替える。

```text
ActionExecutor
├─ IRDeviceExecutor
├─ GenericHTTPExecutor
├─ NatureRemoExecutor
└─ その他の外部API Executor
```

# 9. API概要

| **メソッド / パス**               | **用途**                         | **利用者** |
|-----------------------------------|----------------------------------|------------|
| **POST /internal/detections**     | 認識イベント受信                 | Python     |
| **GET /api/cameras**              | カメラ一覧取得                   | フロント   |
| **GET /api/motions**              | 固定モーション一覧取得           | フロント   |
| **GET /api/appliances**           | 家電一覧取得                     | フロント   |
| **POST /api/appliances**          | 家電追加                         | フロント   |
| **POST /api/actions**             | 家電操作追加                     | フロント   |
| **POST /api/bindings**            | カメラ・モーション・操作の紐付け | フロント   |
| **POST /api/actions/:id/execute** | 操作の手動テスト                 | フロント   |
| **GET /api/logs**                 | 操作ログ取得                     | フロント   |

# 10. 実行フロー

1. XIAO ESP32S3 SenseがMJPEG映像を配信する。
2. 対応するPythonワーカーがMJPEGを受信する。
3. PythonがPoseとHandsを解析する。
4. 固定ルールに一致した場合、認識イベントをGoへ送信する。
5. Goがevent_idの重複とクールダウンを確認する。
6. Goがcamera_idとmotion_codeから紐付け済みの操作を取得する。
7. Goがprovider_typeに対応するExecutorを選択する。
8. Executorが自作赤外線端末または外部HTTP APIを呼び出す。
9. 結果をaction_logsへ記録する。

# 11. 障害時の挙動

| **障害**              | **挙動**                                                         |
|-----------------------|------------------------------------------------------------------|
| **カメラ切断**        | 該当Pythonワーカーが再接続する。他方のカメラ処理は継続する       |
| **MJPEG受信遅延**     | 古いフレームを破棄し、最新フレームを優先する                     |
| **Python→Go送信失敗** | 短時間で数回再送し、それでも失敗した場合はログへ記録して破棄する |
| **外部API失敗**       | エラーを記録し、無制限には再送しない                             |
| **同一イベント再送**  | event_idで重複排除する                                           |
| **同一ポーズ維持**    | 通常姿勢へ戻るまで再発火しない                                   |

# 12. デモ運用

- 各カメラの前に立ち位置を示すテープまたは案内表示を置く。
- カメラ正面を向き、手が画面外へ出ない距離に立つ。
- デモ開始前に2台の映像、Pythonワーカー、Go API、DB、操作対象機器の疎通を確認する。
- 操作対象機器は、手動実行APIで事前に動作確認する。
- 認識しづらい場合に備え、照明条件とカメラ角度を固定する。

# 13. 非機能要件

| **項目**         | **要件**                                                           |
|------------------|--------------------------------------------------------------------|
| **遅延**         | ポーズ成立から機器操作開始まで、デモ上違和感のない範囲を目標とする |
| **可用性**       | 片方のカメラまたはワーカーが停止しても、もう片方は継続動作する     |
| **保守性**       | 認識、バックエンド、外部API実行を分離する                          |
| **拡張性**       | Executor追加により新しい操作方式へ対応できる                       |
| **セキュリティ** | 同一LAN内で運用し、外部へポート公開しない                          |
| **プライバシー** | 映像を保存せず、個人識別を行わない                                 |

# 14. 実装前に残っている決定事項

- MVPで認識する具体的なポーズ・モーションの一覧
- 各ポーズ・モーションの判定条件、維持時間、閾値
- 各カメラに割り当てる操作対象
- MVPで使用する外部APIまたは自作赤外線端末の種類
- フロントエンドの画面構成
- 初期クールダウン時間

# 15. MVP完成条件

1. 2台のXIAOからMJPEG映像を安定して配信できる。
2. 2つのPythonワーカーがそれぞれ独立して映像を受信できる。
3. PoseとHandsを用いて固定ポーズまたは固定モーションを認識できる。
4. PythonからGoへcamera_id付きの認識イベントを送信できる。
5. GoがDBから紐付けを取得できる。
6. Goが自作赤外線端末または外部HTTP APIを呼び出せる。
7. 2台のカメラで同じ動作に異なる操作を割り当てられる。
8. 同じ動作の連続実行を防止できる。
9. 片方のカメラが切断しても、もう片方が動作を継続できる。
10. 操作結果とエラーをログで確認できる。

現行実装では、上記7の「同じ動作にカメラごとに異なる操作を割り当てる」要件だけ未達であり、その他のカメラID伝播・グローバル紐付け・クールダウンの動作を先行実装している。

# 16. まとめ

本MVPは、2台のカメラを別々の入力として使用し、PythonでPoseとHandsを認識し、Goバックエンドが認識結果に対応する家電操作または外部APIを実行する構成とする。映像通信には、実機で安定動作を確認できたHTTP MJPEGを採用する。ポーズ・モーションは事前定義とし、登録機能はMVP対象外とする。
